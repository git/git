# Q2 2026 Plan

## Quarter

- Quarter: Q2
- Year: 2026
- Planning owner: AcreetionOS co-leads
- Date drafted: 2026-05-06

## Strategic Theme

- Primary theme: make Ace legible and dependable as a Git-native workflow platform
- Why this theme matters now: the repository already has the beginnings of a strong product identity, but the core workflow and project narrative need to become more coherent before larger ambitions are credible
- Which user group it serves: advanced Git users, maintainers, stacked-change workflows, and teams that care about sovereignty and operator control

## Top Goals

## Goal 1

- Goal: strengthen the `git ace` workflow surface
- User problem: users need branch-tree workflows they can trust, not just demonstrate
- Success metric: clearer docs, stronger metadata safety narrative, and better defined near-term implementation targets around rename/delete/status/conflict flows
- Maturity target: supported but evolving

## Goal 2

- Goal: make the project easier to understand as a product and organization
- User problem: without a clear narrative, contributors and users cannot easily tell what is core, what is experimental, and what AcreetionOS is trying to build
- Success metric: a coherent project-summary set covering internals, roadmap, governance, release criteria, and ownership
- Maturity target: stable documentation baseline

## Goal 3

- Goal: define release and planning discipline for Ace
- User problem: ambitious projects often over-claim maturity and under-document delivery expectations
- Success metric: usable release criteria, a 1.0 release policy, and an actionable planning template filled in for the current quarter
- Maturity target: stable organizational process baseline

## Planned Deliverables

- Command or feature changes:
  clarify and prioritize the next steps around `git ace`, `git history`, `git replay`, and repository-introspection commands through roadmap and release docs
- Documentation changes:
  complete the project-summary system so it functions as a living product and governance overview
- Test and verification work:
  define stronger expectations around tests for ref, history, and Ace metadata changes
- Release or migration work:
  establish the standard for what Ace 1.0 should require

## Risks

- Compatibility risks: future workflow ambitions could accidentally pressure the project away from Git-native clarity
- Operational risks: a two-person leadership model can create bottlenecks across engineering, documentation, support, and release work
- Documentation risks: roadmap ambition can outrun implementation reality if not labeled carefully
- Staffing or ownership risks: too many important functions still depend on a very small number of people

## Out Of Scope

- Explicitly deferred work:
  fully implementing all roadmap features this quarter
- Nice-to-have work not committed this quarter:
  complete agent-native workflow design, full review-series management, and operator-grade dashboards

## Exit Criteria

- What must be true by the end of the quarter:
  the project has a coherent documented identity, release posture, governance summary, and ownership model
- What will count as partial success:
  the docs and release expectations are strong even if the code changes remain incremental
- What will be left for the next quarter:
  implementation and testing work that turns the roadmap into deeper command behavior
